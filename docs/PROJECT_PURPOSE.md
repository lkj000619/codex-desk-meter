# Codex Desk Meter 프로젝트 목적

## 1. 프로젝트 개요

Codex Desk Meter는 OpenAI Codex의 사용 상태를 컴퓨터 화면을 전환하지 않고
책상 위에서 지속적으로 확인할 수 있게 하는 물리적인 외부 디스플레이
프로젝트다.

이 프로젝트는 다음 두 결과물을 함께 만드는 것을 목적으로 한다.

1. Codex 사용량과 리셋 정보를 실시간에 가깝게 보여주는 데스크 디바이스
2. 동일한 개발 과제를 여러 AI 에이전트에 수행시켜 결과 품질, 토큰 사용량,
   작업 시간을 비교할 수 있는 재현 가능한 실험 자료

따라서 최종 결과는 펌웨어나 장치 하나에 한정되지 않는다. 요구사항, 데이터
출처, 하드웨어 구성, 구현 과정, 평가 방법 및 원시 측정 결과까지 다른 사람이
검토하고 다시 실행할 수 있는 형태로 남기는 것을 포함한다.

## 2. 해결하려는 문제

Codex를 장시간 사용하는 동안 사용자는 남은 사용량과 리셋 시점을 확인하기
위해 별도의 화면이나 명령을 열어야 한다. 또한 정기적인 개인 사용량 리셋과
간헐적으로 발생하는 글로벌 사용량 리셋은 성격이 다르지만 한눈에 구분해서
확인할 수 있는 물리적 장치는 찾기 어렵다.

한편 AI 에이전트를 활용한 개발에서는 동일한 요구사항을 주어도 에이전트마다
설계, 구현 완성도, 작업 시간과 토큰 소비가 달라진다. 단순한 인상 평가가
아니라 동일 조건에서 이 차이를 기록하고 비교할 수 있는 실험 구조가 필요하다.

Codex Desk Meter는 이 두 문제를 하나의 실제 임베디드 프로젝트를 통해
다룬다.

## 3. 제품 목표

### 3.1 핵심 목표

- Codex의 개인 사용량 상태를 명확한 퍼센트 또는 진행 상태로 표시한다.
- 개인 사용량 창의 다음 리셋 시각과 남은 시간을 표시한다.
- 최근 글로벌 리셋의 발생 시각과 경과 시간을 표시한다.
- 다음 글로벌 리셋에 대한 예측이 제공되는 경우 확률과 신뢰도를 표시한다.
- 네트워크 또는 데이터 제공처에 장애가 있어도 마지막 정상 데이터를
  유지하고, 현재 데이터가 오래되었음을 사용자에게 알린다.
- 책상 위에 계속 두고 사용할 수 있도록 정보 가독성, 조작 단순성 및 안정성을
  우선한다.

### 3.2 정보의 의미 구분

장치는 다음 정보를 서로 다른 개념으로 취급해야 한다.

- **개인 사용량:** 사용자의 Codex 계정에 적용되는 실제 사용량 상태
- **개인 리셋:** 개인별 사용량 창이 갱신되는 시각
- **글로벌 리셋:** 전체 또는 특정 범위의 사용자에게 간헐적으로 제공되는
  사용량 초기화
- **Banked reset:** 즉시 사용량을 초기화하지 않고 사용자가 나중에 적용할 수
  있는 리셋 권리
- **리셋 예측:** 과거 이력과 공개 신호를 기반으로 한 확률적 정보

확정된 상태와 외부 서비스의 예측은 화면에서 혼동되지 않아야 한다. 예측값은
그 자체로 확정된 리셋 일정이나 보장을 의미하지 않는다.

### 3.3 데이터 출처 원칙

- 개인 사용량과 개인 리셋 정보는 사용자의 Codex 상태를 가장 직접적으로
  반영하는 출처를 우선한다.
- 글로벌 리셋 기록과 예측에는 `codex-resets.com`, `codex-reset.com` 등 외부
  데이터 제공처를 사용할 수 있다.
- 외부 제공처의 값은 출처, 조회 시각, 데이터 종류와 함께 관리한다.
- 서로 다른 제공처의 이벤트 수나 시각이 다를 수 있으므로 이를 하나의 확정
  값으로 임의 병합하지 않는다.
- 웹 페이지의 표시 구조에 직접 의존하기보다 공개된 구조화 API가 있으면 이를
  우선한다.
- 데이터 제공처가 중단되거나 형식을 변경해도 장치 전체가 동작 불능이 되지
  않도록 수집 계층을 분리한다.

## 4. 하드웨어 목표

동일한 정보 모델과 핵심 기능을 두 가지 하드웨어 구성으로 구현한다.

### 4.1 버전 1: 조립형 소형 디바이스

- MCU: ESP32-S3 Super Mini
- 디스플레이: 1.8인치 SPI TFT LCD
- 해상도: 160 × 128
- LCD 컨트롤러: ST7735S
- 입력: 외부 스위치 2개

이 버전은 보유 부품을 활용한 소형·저비용 장치 구현과 직접 배선 방식의 개발
과정을 검증한다. 제한된 화면 크기 안에서 핵심 정보를 빠르게 읽을 수 있는
간결한 UI를 목표로 한다.

### 4.2 버전 2: LCD 일체형 디바이스

- 보드: Waveshare ESP32-S3-LCD-3.16
- 디스플레이: 온보드 3.16인치 LCD
- 해상도: 320 × 820
- LCD 컨트롤러: ST7701
- 입력 및 주변 장치: 보드에 내장되거나 보드가 제공하는 I/O 범위에서 사용

이 버전은 외부 부품과 배선을 최소화하고 일체형 보드만으로 완성도 높은
데스크 디스플레이를 구현하는 것을 목표로 한다. 세로로 긴 화면을 활용해 개인
사용량, 리셋 상태와 최근 이벤트를 더 풍부하게 표현할 수 있어야 한다.

### 4.3 두 버전의 공통 원칙

- 데이터의 의미와 통신 형식은 두 장치에서 동일하게 유지한다.
- 네트워크, 시간, 데이터 파싱과 상태 관리 로직은 가능한 한 공유한다.
- 디스플레이와 입력 처리는 보드별 구현으로 분리한다.
- 한 버전의 기능 변경이 다른 버전의 전면 재구현을 요구하지 않도록 한다.
- 보드별 해상도 차이를 고려해 화면 배치는 별도로 최적화한다.

### 4.4 개발 순서

초기 개발과 AI 에이전트 비교 실험은 버전 2를 기준으로 진행한다. Waveshare
ESP32-S3-LCD-3.16 보드에서 전원, USB 연결, 제조사 기본 예제와 LCD 동작을 먼저
확인한 뒤 데이터 수집, 상태 관리, 네트워크, 입력, 화면 표시 및 장애 복구의
기준 구현을 개발한다.

버전 1은 부품을 확보하고 빵판에 배치했지만 회로 구성이 완료되지 않았다.
따라서 버전 2의 기준 구현 이후 후속 단계에서 회로 구성과 하드웨어 이식을
진행한다.

### 4.5 기준 개발 프레임워크

두 하드웨어 버전의 기준 펌웨어는 Espressif의 공식 프레임워크인 ESP-IDF로
개발한다. 빌드, 테스트와 업로드는 GUI 조작에 의존하지 않고 `idf.py` 명령으로
재현할 수 있어야 한다. 구체적인 ESP-IDF 버전은 두 보드, 디스플레이 및
Waveshare 공식 예제와의 호환성을 검증한 뒤 별도 개발 환경 문서에서 고정한다.

Zephyr RTOS를 비롯한 다른 프레임워크의 포팅은 기준 구현이 완성된 이후 수행할
수 있는 별도 비교 실험으로 취급하며, 초기 필수 범위에는 포함하지 않는다.

## 5. AI 에이전트 실험 목표

이 프로젝트는 제품 개발과 별도로 AI 에이전트의 개발 수행 능력을 비교하는
실험을 포함한다.

### 5.1 확인하려는 질문

- 같은 요구사항을 받은 에이전트들은 어떤 구조와 구현을 제안하는가?
- 어느 결과가 실제 빌드 및 하드웨어 동작 조건을 더 잘 만족하는가?
- 공통 코드와 보드별 코드를 얼마나 적절하게 분리하는가?
- 완료까지 얼마나 많은 시간과 토큰을 사용하는가?
- 오류 상황과 불완전한 정보에 얼마나 견고하게 대응하는가?
- 동일 에이전트를 반복 실행했을 때 결과가 얼마나 일관적인가?
- 동일한 하드웨어 사양에서 에이전트마다 어떤 추가 기능을 발견하고 선택하는가?

### 5.2 비교 대상

비교 대상은 특정 에이전트나 모델로 고정하지 않는다. 실험 시점에 선택한 AI
에이전트, 모델, 추론 수준, 도구 사용 조건과 버전을 실행 결과에 함께 기록한다.

### 5.3 측정 방향

실험에서는 최소한 다음 항목을 수집한다.

- 시작 및 종료 시각과 총 소요 시간
- 입력, 출력, 캐시 및 총 토큰 수(제공되는 범위에서)
- 실행한 도구와 명령 수 및 실패 횟수
- 빌드 성공 여부와 자동 테스트 결과
- 요구사항 충족률
- 실제 하드웨어 검증 결과
- 코드 품질, 재사용성 및 문서 완성도
- 사용자 개입 및 추가 질문 횟수

토큰이나 시간이 적다는 사실만으로 좋은 결과로 평가하지 않는다. 기능과
안정성을 우선 평가하고 비용과 시간은 별도의 효율 지표로 함께 제시한다.

### 5.4 공정성과 재현성 원칙

- 모든 비교 실행은 동일한 기준 커밋에서 시작한다.
- 동일 비교군에는 동일한 요구사항과 입력 자료를 제공한다.
- 에이전트별 구현은 서로 독립된 브랜치 또는 worktree에서 수행한다.
- 최초 프롬프트, 추가 대화, 명령 로그, 결과와 실패 기록을 보존한다.
- 실패한 실행도 결과에서 제거하지 않는다.
- 모델, 도구, 네트워크 접근, 제한 시간 등 결과에 영향을 주는 조건을 기록한다.
- 가능하면 같은 조건을 여러 번 실행하여 평균뿐 아니라 결과 편차도 확인한다.

### 5.5 하드웨어 기반 자율 기능

각 에이전트에는 동일한 대상 보드의 하드웨어 기능 카탈로그를 제공한다.
에이전트는 핵심 제품 요구사항을 구현하는 것과 별도로, 실제 온보드 자원을
활용해 사용자 가치가 있는 추가 기능을 스스로 발굴하고 구현한다.

기본 비교 실행에서는 에이전트가 기능 후보 3개를 제시한 뒤 그중 1개를 직접
선택한다. 사용자에게 후보 선택을 넘기지 않으며, 후보별 근거와 선택하지 않은
이유도 남긴다. 추가 기능은 핵심 기능의 합격 기준과 분리해 평가한다.

Version 2 전용 IMU, RTC, 배터리 ADC, TF 카드 또는 BLE 등의 활용은 허용하지만
Version 1의 필수 기능으로 자동 승격하지 않는다. 추가 하드웨어를 연결하거나
핵심 요구사항을 축소하는 선택은 기본 실험에서 허용하지 않는다. 세부 절차는
[하드웨어 기반 자율 기능 실험](experiments/hardware-feature-discovery.md)을
따른다.

## 6. 저장소의 역할

기준 브랜치는 프로젝트를 이해하고 실험을 다시 시작할 수 있는 출발점이다.
기준 브랜치에는 다음 내용을 유지한다.

- 프로젝트 목적 및 요구사항
- 하드웨어와 데이터 프로토콜 명세
- 대상 보드의 고정 하드웨어 기능 카탈로그
- 실험 프롬프트와 평가 기준
- 에이전트 자율 기능 선택 구성
- 실행 및 측정 방법
- 결과 데이터 형식과 검증된 집계 자료
- clone 후 실험을 준비할 수 있는 최소 도구

개별 에이전트가 작성한 제품 구현, 원본 로그와 해당 실행의 상세 결과는 별도
실험 브랜치에서 관리한다. 검증된 요약 통계는 출처가 되는 브랜치와 커밋을
명시한 뒤 기준 브랜치에 반영할 수 있다.

## 7. 프로젝트 성공 기준

프로젝트는 다음 조건을 충족할 때 목적을 달성한 것으로 본다.

1. 두 하드웨어 버전에서 Codex 사용량과 리셋 정보를 식별 가능하게 표시한다.
2. 개인 상태, 글로벌 리셋 및 예측 정보가 서로 혼동되지 않는다.
3. 일시적인 네트워크 장애나 잘못된 데이터가 장치 중단으로 이어지지 않는다.
4. 동일한 핵심 데이터 모델을 두 하드웨어 구현이 공유한다.
5. 제3자가 기준 브랜치를 clone하여 문서만으로 실험 조건을 이해하고 실행을
   준비할 수 있다.
6. 에이전트별 결과에 시간, 토큰, 테스트 및 품질 지표가 함께 남는다.
7. 측정 결과에서 구현 품질과 실행 효율을 근거를 들어 비교할 수 있다.
8. 각 에이전트의 하드웨어 기반 추가 기능 후보·선택·구현 결과를 핵심 기능과
   분리해 비교할 수 있다.

전체 프로젝트의 성공 기준은 두 버전을 포함하지만, 초기 단계의 완료 기준은
버전 2의 빌드, 업로드 및 실제 하드웨어 동작 검증으로 한정한다. 버전 1은 회로
구성 후 동일한 기준으로 별도 검증한다.


## 8. 현재 범위 밖의 항목

초기 프로젝트에서는 다음 항목을 필수 목표로 하지 않는다.

- OpenAI 또는 외부 데이터 제공처가 공개하지 않은 계정 정보의 우회 수집
- 리셋 예측을 확정 일정으로 보장하는 기능
- Codex 사용량을 늘리거나 제한을 우회하는 기능
- 모바일 앱 또는 범용 스마트홈 플랫폼 개발
- 상용 제품 수준의 대량 생산, 인증 및 유통
- 모든 ESP32 계열 보드와 디스플레이에 대한 범용 지원

이 항목들은 핵심 제품과 실험 체계가 검증된 이후 별도의 범위로 검토한다.
