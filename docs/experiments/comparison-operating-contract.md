# 첫 결과와 후속 수정 비용 비교 운영 계약

상태: **2026-10-02 운영 도구·실제 CLI 준비·공통 입력 동결 반영. 본 실험은 미실행이며 실물 기능 관측은 후보 실행 이후 수행.**

이 문서는 [2026-09-29 방향 전환](reference-comparison-20260929.md)을 구체화한다.
사용자는 2026-10-02에 아래 목표·예산·보드 제공 수준을 선택했다.
문서 업데이트 자체로 새 후보 실행이나 중지한 OpenCode 작업을 재개하지 않는다.

## 1. 적용 범위와 문서 우선순위

다음 새 동일 조건 비교의 운영 규칙은 이 계약을 따른다. 기존 pilot·단회 실행의
protocol·approval·원본 판정은 당시 조건의 역사 기록으로 유지한다.

1. 명시적 사용자 지시와 이 계약의 채택된 운영 조건.
2. [reference-match 목록](reference-match-matrix.md)의 기준 도달 판정.
3. [제품 계약](../PRODUCT_CONTRACT.md)의 전체 제품 합격 조건과 데이터 의미.
4. [평가 계약](evaluation-contract.md)의 요구별 시험·증거 경계.
5. schema·validator의 실제 기계 계약. 문서와 다르면 결함으로 수정하고 임의로
   새로운 JSON 필드를 요구하지 않는다.

아래 변경은 기존 단회 규칙을 과거 실행에 소급하지 않는다.

| 기존 조건 | 다음 새 비교에 적용할 조건 |
|---|---|
| prompt 1회·실행 중 후속 질문/구현 피드백 0회 | 최초 실행에는 그대로 적용 |
| 후속 수정은 원본 순위에서 제외 | 종료 후 별도 수정 회차로 보존하고 reference 도달 비용에 합산 |
| pilot 전체 합격 뒤 본 실험 | 실행 인프라의 준비와 제품 품질을 구분. 후보의 제품 실패도 결과로 기록 |
| 전체 제품 합격을 유일한 완료로 해석 | reference-match와 production-conformance를 분리 |

현재 `version-2-baseline.yaml`·최초 prompt에 채택 조건을 반영했다.
후보는 [allowlist](../../experiments/config/agent-inputs.json)의 실행 과제·제품 계약·보드 자료
3개와 필요한 기계 입력만 제공받는다. 이 운영 문서·평가 원본·과거 기록은 복사하지 않는다.
후속 feedback·예산 manager·reference 판정·전체 실패 비용·관측·복원 도구는
[도구 안내](comparison-tooling.md)에 연결했다. baseline 동결 상태와 실제 관측 완료는
[준비 상태](next-comparison-readiness.md)에서 별도로 관리한다.

## 2. 기준 도달과 전체 합격

**사용자 선택 Q1: Codex에서 확인된 기능 도달을 비교하고 전체 계약 합격은 별도로 판정.**

- `reference-match`: 고정된 기준 목록에서 확인된 필수 동작을 같은 stimulus로
  재현한 상태다. 기준 제품에 없는 기능이나 미입증 상태를 합격 전제로 추가하지 않는다.
- `production-conformance`: C1~C8·I1~I4·F1~F9와 해당 증거를 기존 제품 계약대로
  검토한 상태다. `product_pass`는 기존 schema 의미를 유지한다.
- reference 도달만으로 `product_pass: true`를 쓰지 않는다. 미검증은 pass가 아니다.
- 기준 Codex는 `7923f96`의 fixture 제품이다. 운영자 기여가 포함된 기준 제품이며
  독립 Codex 첫 실행의 순위 자료가 아니다.

위 두 용어는 비교 해석 이름이다. 현재 result schema에 없는 새 top-level 필드를
후보 JSON에 임의로 추가하지 않는다. reference 판정은 별도 RM review JSON과 comparison
ledger에 연결하며, 형식과 `comparison.py review` 절차는 [도구 안내](comparison-tooling.md)를 따른다.

## 3. 실행·수정 예산

**사용자 선택 Q2: 후속 최대 3회·누적 120분. 최초 실행은 기존 120분 한도를 유지.**

| 단계 | 한도 | 집계 |
|---|---|---|
| 최초 실행 | 최대 7,200초 | 공통 최초 prompt 전달부터 프로세스 종료까지 |
| 후속 수정 | 최대 3회, 수정 전체 누적 7,200초 | 각 종료 후 별도 지시로 시작한 후보 session 시간 합 |
| 후보 실행 총합 | 최대 14,400초 | 최초 실행+후속 수정; 각 단계 한도도 각각 적용 |

수정 한 회차의 허용 시간은 남은 후속 누적 예산을 넘을 수 없다. 실행 내의 자체
edit·build·재시험은 별도 수정 회차로 세지 않는다. 시작된 실패·timeout·중단 회차도
수정 회차와 소비 시간에 포함한다. 후보에게 전달하지 않은 환경 준비는 회차로 세지 않는다.

reference 도달, 수정 3회 소진, 후속 누적 시간 소진 또는 사용자 중지 시 종료한다.
한도 종료는 `미도달`로 보존하며 빠른 성공으로 해석하지 않는다.
환경 수리·피드백 작성·독립 검증·업로드·실물 평가 시간과 운영자 비용은 별도 기록한다.

### 3.1 전체 실행 규모와 관측 일정

2026-10-04 갱신. baseline의 모델별 독립 반복 3회는 후속 수정 3회와 다르다.
사용자가 Claude를 제외하여 현재 5개 agent/model 조합은 [준비 상태](next-comparison-readiness.md)의 목록을 따른다.
10월 3일의 6개/18개 최초 series/72시간 계산은 당시 구성 기록이며 현재 계획에 적용하지 않는다.

| 단계 | 최초 실행 | 후속 실행 상한 | 후보 실행 시간 합의 상한 |
|---|---:|---:|---:|
| 1블록: 각 조합의 독립 반복 1회 | 5회 | 15회 | 20시간 |
| 2블록: 각 조합의 독립 반복 2회 | 5회 | 15회 | 20시간 |
| 3블록: 각 조합의 독립 반복 3회 | 5회 | 15회 | 20시간 |
| 전체 | 15회 | 45회 | 60시간 |

상한은 최초 회당 2시간과 독립 series당 후속 누적 2시간을 합산한 값이다.
회당 후속 2시간씩 3회를 더하는 계산이 아니다. 실제 조기 종료·도달 시 더 짧으며 준비·피드백 작성·
독립 평가·flash·실물 관측 시간은 별도다. 이 표는 달력상 60시간 안에 끝난다는 약속이 아니다.

블록 시작 전 모델 순서·난수 seed·독립 반복 번호·baseline/profile·평가 버전을 기록한다.
후속은 그 최초 실행의 series에 연결하며 다음 독립 반복에 코드를 넘기지 않는다.
한 보드의 업로드·관측 슬롯은 직렬 배정한다. 슬롯마다 run/artifact hash, 담당자,
예정/실제 시각, 공통 fixture·촬영 조건, 종료 시 보드 상태를 남겨 다른 후보 증거와 섞이지 않게 한다.

각 최초/후속 종료 후 먼저 결과를 동결·평가하고 잔여 예산 안에서 다음 회차를 결정한다.
reference 도달·회차/예산 소진·사용자 중지 조건은 3절을 따른다. 블록 경계에서는 누락 증거·
환경 변경·비용 coverage를 검토하고 다음 블록 일정을 기록한다. 결과가 나쁘다는 이유로 실패 run을
삭제하거나 독립 반복을 성공할 때까지 대체하지 않는다. 전체 중단 시 완료한 블록 수와 사유를 공개하고
3회 미만을 정식 반복 완료로 표시하지 않는다.

## 4. 동일 입력과 하드웨어 경계

**사용자 선택 Q3: 보드 핀·극성·설정 사실과 제조사 소스만 제공하고 BSP 구현도 평가.**

- 제품 코드 없는 동일 시작 commit, 공통 prompt template, fixture·schema·정책과
  제조사 source 목록/hash를 모든 후보에 제공한다.
- 핀 역할·백라이트 극성·PSRAM/framebuffer·LCD API의 사실과 source 근거는
  [보드 카탈로그](../hardware/version-2-capabilities.md)에서 관리한다. 실제 USB/UART
  경로·시각 기준·관측 장치 설정은 [평가 절차](evaluation-contract.md)에 따른 실행 기록으로
  확인한다. 미확인 설정을 공통 보드 사실로 채우지 않는다.
- 검증된 공통 BSP나 Codex/다른 후보의 제품 source·patch를 제공하지 않는다.
  BSP 구현과 수정에 소비한 자원도 후보 실행 비용에 포함한다.
- provider/model/설정은 최초 실행부터 후속 수정까지 보존한다. 변경한 시도는
  동일 조건 도달 비용으로 합치지 않고 변경 조건을 기록한다.
- 실제 계정 수집은 별도 owner-only live 통합이다. fixture 값을 실 계정 잔여량으로 표현하지 않는다.

## 5. 첫 결과 보존과 후속 피드백

최초 종료 시 코드·원본 결과·실행 시간·원본 token·도구/명령·실패·개입을 동결한다.
종료 후 evaluator가 후보 source 수정 없이 공통 평가하고 운영자가 artifact를 관측한다.
실패도 결과로 남기며 같은 첫 결과를 성공할 때까지 다시 실행하지 않는다.

후속은 자신의 직전 frozen 결과에서 시작한다. 매 회차의 피드백은 다음 내용을 기록한다.

| 필수 내용 | 의미 |
|---|---|
| 직전 run/commit | 어떤 결과에서 이어서 수정하는가 |
| 목표 항목 ID | reference-match 또는 제품 요구의 대상 |
| 관측 | 로그·값·화면·오류와 관측 범위 |
| 기대 동작 | 고정 평가 목록이 요구하는 결과 |
| 근거 | 원본 evidence 위치/hash, source 관측이면 해당 파일 |
| 남은 예산 | 남은 회차와 후속 후보 실행 초 |

구현 방법·다른 후보 코드·운영자 제품 patch를 제공하면 개입으로 기록한다.
후속 피드백 때문에 같은 비교군의 공통 목표·입력을 변경하지 않는다.
실행 중 새 구현 피드백은 최초와 후속 모두 별도 개입으로 보존하며 비교 적격성을 검토한다.

## 6. 결과 해석과 후속 작업

실행 상태, 정책 준수, C/F/I 기능, reference 도달, product_pass, 비교 적격성을
별도 결과로 읽는다. 원본 token 정의를 보존하고 provider total의 직접 비용 순위를
만들지 않는다. 최초·회차별·누적의 집계 범위를 명시한다.

입력 동기화·capability·복원 및 관측 도구의 현재 상태는 [준비 상태](next-comparison-readiness.md)가
관리한다. [정비 계획](../plans/2026-10-02-experiment-contract-remediation.md)은 작업의 근거와 완료 조건을
보존한다. 실제 후보 production 연결·실물 관측은 후보 실행 후 수행한다.
기존 과거 실행을 이 계약과 동등한 새 반복으로 편입하지 않는다.
