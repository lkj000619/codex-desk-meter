# ADR-0001: 기준 펌웨어 프레임워크로 ESP-IDF 사용

- 상태: 승인
- 결정일: 2026-09-05

## 배경

Codex Desk Meter는 ESP32-S3 Super Mini와 Waveshare
ESP32-S3-LCD-3.16을 대상으로 한다. 두 하드웨어에서 공통 애플리케이션 로직을
공유하면서 디스플레이와 입력 장치만 보드별로 분리해야 한다. 또한 여러 AI
에이전트의 구현 결과를 비교하므로, 개발자의 IDE 설정에 의존하지 않는 동일한
빌드·테스트·업로드 절차가 필요하다.

## 결정

프로젝트의 기준 펌웨어 프레임워크로 ESP-IDF를 사용한다.

- 명령행 작업의 기준 도구는 `idf.py`로 한다.
- 두 보드의 빌드는 동일한 ESP-IDF 설치에서 재현 가능해야 한다.
- Wi-Fi, HTTP/TLS, 시간 동기화, NVS와 LCD 지원은 ESP-IDF의 공식 기능을
  우선 사용한다.
- GUI가 필요한 화면에서는 LVGL 사용을 허용하되 구체적인 버전은 별도로
  고정한다.
- VS Code와 ESP-IDF 확장은 선택 가능한 개발 보조 도구로만 취급한다.
- ESP-IDF와 종속성의 버전은 `latest`로 두지 않고 검증된 버전 또는 커밋으로
  고정한다.

## 이유

- 두 대상 모두 ESP32-S3이며 ESP-IDF가 제조사의 공식 프레임워크다.
- Waveshare 보드의 RGB LCD와 제조사 예제를 활용하기에 유리하다.
- `idf.py` 기반 절차를 문서와 자동화 스크립트에서 동일하게 사용할 수 있다.
- 네트워크 장애 복구, 메모리 관리 및 장시간 동작에 필요한 ESP32 기능을 직접
  사용할 수 있다.
- 호스트 테스트와 실제 하드웨어 테스트를 분리하기에 적합하다.

## 영향

- 기준 브랜치의 요구사항과 테스트는 ESP-IDF 프로젝트를 전제로 작성한다.
- 에이전트 비교 실행에서 프레임워크 선택은 평가 대상이 아니라 고정 조건이다.
- 보드별 핀, LCD 초기화와 빌드 설정은 별도 설정으로 관리해야 한다.
- Waveshare 예제를 그대로 복사하기보다 필요한 초기화 정보와 설정을 출처와
  라이선스에 맞게 가져와야 한다.

## 대안

### Arduino framework

초기 프로토타이핑은 빠르지만 IDE의 수동 설정과 코어·라이브러리 버전 차이가
비교 실험의 재현성을 낮출 수 있어 기준 프레임워크로 선택하지 않았다.

### PlatformIO

다중 빌드 환경 관리에는 유용하지만 자체 펌웨어 프레임워크가 아니며,
Arduino-ESP32 및 보드 패키지 버전 호환성이 추가 변수가 될 수 있어 기준 빌드
도구로 선택하지 않았다.

### Zephyr RTOS

Devicetree, Kconfig 및 자동 테스트 체계가 매력적이지만 Waveshare 보드의 RGB
LCD를 포함한 초기 보드 포팅 비용이 크다. 기준 구현 완성 후 선택적인 비교
실험 대상으로 유지한다.

## 미결정 사항

- 사용할 LVGL 여부와 정확한 버전
- 두 보드의 보드 정의 및 빌드 선택 방식
- 실제 업로드 포트 자동 탐지 정책

이 사항은 하드웨어 bring-up과 제조사 예제 호환성 검증 후 별도 결정 문서에서
확정한다.

ESP-IDF의 초기 기준 버전은
[ADR-0004](0004-pin-esp-idf-5.3.2.md)에서 v5.3.2로 확정했다.
